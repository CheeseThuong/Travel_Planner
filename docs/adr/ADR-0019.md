# ADR-0019 — Disposable local Supabase and catalog schema mapping

Status ACCEPTED implementation detail under current continuation request, 2026-10-22. Depends on G1 PASS. No hosting/production/schema bypass.

Use Supabase CLI2.121.0 (MIT) as an exact dev dependency, following the official [CLI workflow](https://supabase.com/docs/guides/local-development/cli/getting-started). Registry metadata includes jose6 MIT and eciesjs0.5 MIT (Node>=16). Native optional platform packages are tooling only; no application imports or client bytes. Audit the resolved tree after install and run the binary on this host. No globally installed CLI or shell installer. Docker29.8.2 is already running. Node24/npm11 remain unchanged.

Master destinations/places remain canonical. Map original seed editorial_hours to hours_json, image.path to image_key, data_source.license to content_license. Preserve the complete original record in editorial_metadata JSONB, with source/license/caution/image/coordinate-quality metadata available without lossy reconstruction. Both destinations and places start draft; read policies require published place AND published destination. Seed generator uses fixed UUIDs per city, original place UUIDs, no runtime network and safely quoted JSON/SQL. No Google content is acquired or stored.

Constraints implement reviewed Master ranges, city FK, unique city/slug, and unknown-hours consistency. All exposed tables have RLS and explicit least-privilege grants. Public roles can SELECT only through publication policies; no editorial write grant. Tests exercise both public roles and PostgreSQL constraint failures against actual local DB.

The local project has a distinct disposable ID/ports and no Supabase link. Reset/test wrappers reject remote flags, linked project metadata and unexpected project config; no DATABASE_URL input is consumed. CLI startup output containing generated local credentials must not enter committed logs. Alternative raw Postgres container would omit Supabase roles/auth schema and not provide the mandated CLI tests. Full auth/trip ownership is P02-02..04, not inferred from catalog policies.

Use an explicitly labelled Docker bridge restricted to loopback, as documented by [Supabase](https://supabase.com/docs/guides/local-development) and [Docker port publishing](https://docs.docker.com/engine/network/port-publishing/). The wrapper verifies label, bridge driver and binding before CLI execution. Actual published ports must be inspected; do not infer isolation from the project name alone.

Rollback removes new migration/seed/tooling only before deployment, preserving original 60 source records. Once real data exists, use additive forward migrations and verified backup/restore rather than destructive reset. Updated cases: bounds/status/slug/FK rejection, draft isolation, parent destination publication, anon/authenticated read-only, metadata/ID preservation, two-city counts and deterministic seed/reset replay.

Correction after actual CI run39706612712: start succeeded but reset/stop failed because the initial guard rejected every `_current_branch` file. In CLI2.121.0, [startInitCurrentBranch](https://github.com/supabase/cli/blob/v2.121.0/apps/cli/src/command-internal/db-bootstrap/db-setup.ts) and the [documented startup side effects](https://github.com/supabase/cli/blob/v2.121.0/apps/cli/src/commands/start/SIDE_EFFECTS.md) show that normal local startup writes `main` unconditionally when absent. This marker is not a cloud link. A regression test reproduced the failure before correction. Allow only the known local main marker; continue rejecting project-ref files, all other named branches, remote flags, foreign project IDs, remote Docker sockets and non-loopback networks. No security exception or assertion removal.
