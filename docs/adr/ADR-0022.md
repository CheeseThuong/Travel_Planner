# ADR-0022 — Trip budget, party size and user-directed planning

## Context

The user explicitly expanded the product on 2026-10-22: a traveler must enter the trip spending limit and number of travelers, receive a plan and budget result suited to those inputs, and be able to plan personally without the system arranging the itinerary. The original baseline placed basic cost estimates in P1 and had only the assisted planner flow. The catalog has no verified current prices, so the application cannot truthfully infer attraction, meal, lodging or transport prices from place identity alone.

## Decision

Promote the following to P0 and keep each trip in one currency for MVP:

- `party_size` is an integer from1 through30.
- `planning_mode` is `assisted` or `manual`.
- `budget_total_vnd` is an optional whole-VND trip total from0 through1,000,000,000,000. Null means the user has not set a spending limit; zero is valid for a no-spend plan.
- The budget summary separates user-entered fixed estimates (`lodging`, `transport`, `meals`, `other`) from per-stop estimates. Each cost is whole VND and has provenance `user_entered` or `unknown`; MVP does not invent live prices.
- Calculations expose total budget, known estimated spend, remaining known budget, per-person budget, daily group/person allowance, and the count/value of unknown costs. A result can be `within_known_budget`, `over_budget`, or `incomplete_estimate`. `within_known_budget` is never presented as a guarantee when unknown costs remain.
- In `assisted` mode the deterministic planner may create a candidate but applying it still requires confirmation. In `manual` mode Generate is unavailable: the user assigns date, order and local start time. The system validates date/time, overlaps, day bounds, locked stops and budget, but never silently reorders, removes or reschedules user entries.
- Store the expanded fields in the private owner transaction and map them through the verified-owner repository. Existing trips migrate with `party_size=1`, `planning_mode='assisted'`, no budget and unknown costs.

VND uses whole units because it has no commonly used fractional display unit. All arithmetic uses integers and checked bounds; no floating-point currency math. The UI labels values as estimates and shows provenance/unknowns.

## Alternatives

- Infer public prices for every catalog place: rejected because sources are missing, prices change, and it would create false certainty.
- Keep costs only in an unvalidated JSON blob: rejected because owner transactions and calculations need bounded integer contracts.
- Let manual mode call the optimizer and then edit the result: rejected because it does not satisfy the requested personal planning flow and risks rewriting user intent.
- Add multi-currency conversion now: deferred; exchange rates would require another live-data/provenance boundary.

## Consequences and validation

Schema/domain/API contracts expand before G2 closes. P03 builds accessible inputs and manual scheduling controls; P04 adds pure deterministic budget math and assisted cost-aware selection; P05 persists both modes locally and remotely. Tests cover bounds, integer arithmetic, per-person/day calculations, unknown-price honesty, over-budget explanations, manual ordering, overlaps, locked entries, roundtrip persistence and owner isolation. No production price accuracy or booking capability is claimed.
