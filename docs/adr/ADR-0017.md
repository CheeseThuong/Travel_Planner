# ADR-0017 — Maintained ESLint10 with explicit project compatibility adapters

Status: ACCEPTED scoped implementation decision under the user's renewed request to fix blockers and complete the site, 2026-10-21. Verification pending; no gate waiver. Supersedes ADR0014/0015's unresolved tool selection only if the acceptance below passes.

## Context and decision

Installed Next16.4.2 already adapts deprecated RuleContext methods for React/import (`dist/rule-context.js`), but plugin package peer metadata still excludes10. Merely forcing installation or relabeling peers would not resolve compatibility. Use maintained ESLint10.13.0 and **project-maintained, explicitly named snapshots** of React7.37.5, a11y6.10.2 and import2.32.0, each with a real entry adapter using the official `@eslint/compat`2.1.1. Keep every upstream rule/config implementation byte-identical; retain license, original package metadata, hashes and exact-version origin. Declare the tested10 peer on these project packages only; never assert upstream support for these forks. No force/legacy-peer-deps or advisory exceptions.

The adapter restores removed APIs through ESLint's maintained compatibility utility rather than substituting checks. Core ESLint updates remain upstream-maintained; these small adapters/snapshots are maintained by this repository and need revalidation on any version change. Actual `npm ls` and full audit must pass. Existing enabled rule IDs, severity, options and resolver settings must remain unchanged. Existing ten tooling tests remain, with additional adapter/integrity/positive/negative cases. If this cannot pass, retain BLOCKED and roll back task-owned dependency changes.

Strict resolution exposed npm's local-file override/optional-peer interaction. Also snapshot the eight Next-config source/type files unchanged; only its package dependencies point explicitly at the reviewed sibling adapters and existing Next glob patch. Remove global file overrides. This makes real dependency relationships explicit instead of rewriting peers globally. Use `+project.1` build metadata to label project variants while retaining stable-version wildcard compatibility; no upstream version bump claimed. Resolver module installation paths may change; compare actual module identity/options rather than machine-specific absolute paths, with hashes/versions preserved.

Runtime regression exposed duplicate adaptation: Next's older context shim makes official compat detect an older ESLint and miss removed SourceCode methods. Remove exactly the two Next shim calls around React/import in dist/index.js, since the dependencies already supply official adapters. All actual rule/config definitions remain unchanged. Integrity test reverses these exact two substitutions before comparing the original file hash; every other Next config byte is verified unchanged. Portable config comparison normalizes only absolute resolver install paths, preserving module names/entrypoints/options and all rules/severities.

ESLint10 also materializes default options on the already-disabled core `no-unused-vars` rule. Normalize only that inactive rule's trailing defaults in the comparison, retaining its disabled severity and comparing the enabled TypeScript replacement/options exactly. Changing any enabled rule/severity/options or enabling/disabling a rule still fails. Original TypeScript negative fixture remains enforced; baseline JSON is never rewritten.

Tooling-only: zero intentional client import or production bundle dependency. Preserve all notices and verify full resulting audit/license/tree after installation. This is a lint build-tool correction, not a Next/React/database/hosting change. Current request authorizes the implementation; no purchase or external account needed.

Sources: [ESLint10 migration](https://eslint.org/docs/latest/use/migrate-to-10.0.0), [official compatibility utilities](https://github.com/eslint/rewrite/tree/main/packages/compat), public registry exact metadata captured during task; installed Next rule-context inspected directly.

## Alternatives/trade-offs

Waiting for peer metadata leaves progress blocked. Retaining EOL9/paid extended support requires a support contract; none exists. Forcing peers, removing rules, changing to an unrelated linter, or pretending metadata alone proves runtime compatibility are rejected. Vendoring increases review/storage/maintenance; the entry-only adapter, original-byte manifest and exact-version regression checks bound that cost. No promise of upstream support for project forks.
