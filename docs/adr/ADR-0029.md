# ADR-0029 — Owner-scoped candidate RPCs and versioned apply

Status: ACCEPTED implementation detail for explicitly requested P04 generate/apply after G3 PASS,2026-10-28. Separate migration and database tests mandatory; no production action.

## Context and decision

Existing tables already store candidate JSON/schedule metadata but authenticated roles cannot directly write them and no apply RPC exists. Add narrowly scoped security-definer functions owned by `trip_storage_writer` (NOLOGIN/NOBYPASSRLS), using only verified caller JWT identity through the existing UID helper/RLS. Do not use service_role. Generate stores a private candidate and idempotency record without changing trip/version/stops. Apply requires explicit true confirmation and exact current input version; updates all schedule fields and trip version atomically, preserving selected identities, required flags and locks. No direct table grants or policy broadening.

The API accepts only generation options or a stored run ID, not a client candidate. It validates path/header/body, verifies Auth, loads through caller RLS, computes a no-key approximate candidate and persists through RPC. Before apply it recomputes the same candidate and compares canonical JSON to reject tampering. PostgreSQL's owner RPC independently validates candidate shape/IDs/local bounds/locks and CAS/accounting; those database checks do not certify real-world route/hours accuracy. Owner-scoped private candidate storage is an owner data operation, not a public planner oracle. It remains impossible to read/write another owner's records or bypass explicit confirmation/version checks. Direct owner RPC calls cannot escalate ownership; only the HTTP pathway is claimed to validate deterministic engine equivalence. No live Google data is persisted.

Use existing owner-scoped idempotency storage with operation-specific fingerprints and stable response IDs. Same key/different request is409. Generate retries compare candidate content excluding server-generated run UUID; apply retries replay the same version result. Lock trip row after advisory key lock, matching existing save order. Re-check version/ownership inside the transaction; stale run receives PLAN_RUN_STALE without applying. Candidate ID/engine/seed/selected accounting must match.

Align domain/server validation with already tested SQL limits: title120 and lunch/rest0–180. This corrects a permissive validator; no DB constraint is weakened. Future frontend cloud creation/editor remains P05; real Auth tests create disposable owner fixtures through the existing repository to exercise these endpoints.

## Alternatives, risks and rollback

Service-role general CRUD or granting authenticated table writes: rejected. Client-submitted arbitrary apply candidate: rejected. In-memory candidate store: rejected (serverless/reload/idempotency loss). Signed opaque payload/shared signing secret: unnecessary while private durable candidates can be recomputed without live providers. Live traffic matrices would require a different reviewed retention/verification boundary before enabling.

Instance-local API rate limits remain local defense; distributed production limits remain G8. Recompute costs CPU but no paid requests and prepared problems are bounded30 stops. Do not infer production auth/availability or route accuracy from local tests.

Rollback before release: `drop function if exists public.owner_apply_plan(uuid,uuid,integer,uuid,boolean); drop function if exists public.owner_store_plan(uuid,integer,uuid,jsonb); drop function if exists public.trip_store_validate_plan(public.trips,jsonb);` New candidate rows remain private under existing RLS; no user trip/history reset. Test invalid/foreign/anon inputs, tampered/duplicate/missing IDs, lock changes, stale versions, replay and two-owner/parallel CAS on disposable loopback only.
