## Context and decision

The user's Smart Discovery master task expands the original catalog/import/planner scope. Preserve the working Atlas V2, pure deterministic engine, provider ports, owner RLS and generate/confirmed-apply boundary. Complete P04-04/P04-05 before integrating discovery. G4 remains NOT VERIFIED until the user reviews the local evidence; G5–G8 retain their existing requirements. User priority places discovery/import/contributions before Groq and durable editing; record these as gated extension tasks instead of claiming that they complete G5/G6.

The ordered extension index in WORK_ITEMS is authoritative. Each item must specify narrow affected files, acceptance, API/data impact, rollback and tests before implementation. No future task is marked IN_PROGRESS by this amendment.

- Data model: maintain legacy six-category records and IDs; model multiple categories/tags, separate lodging from visits, provider/source/license provenance, coordinate confidence, unknown hours/prices, transport/access constraints and moderation. Use additive migrations and pgTAP transition tests when storage changes; never edit applied migrations or fabricate catalog entries.
- Geography: city-specific data/config for Đà Lạt and Nha Trang, polygon/bounding-box/distance rules; search radius is not an administrative border. Travel-time zones require a provider and clear provenance.
- Discovery: server-only Brave adapter, current official contract/terms review before code, bounded query/page/timeout/quota and retry policy, no-key catalog/fixture fallback. Dedup distinguishes certain identity matches from suggestions requiring confirmation; source rights remain separate. Cache policy must be settled before any external content is persisted.
- Maps: retain ADR0024 no-fetch fallback until a separately reviewed DNS/IP-pinned bounded redirect transport is proven safe and permitted. Do not scrape Maps or infer pin coordinates from camera viewports. Choose a licensed, attributed map service and key/tile policy before adding interactive map selection; no provider dependency is chosen here.
- Contributions: separate user-owned submission/moderation data with validation, spam/rate limits, RLS and audit/reject/restore tests; unreviewed entries cannot overwrite or appear as verified editorial data.
- AI: server-only Groq, configurable currently supported structured-output model, Zod plus known-ID/business validation. Rank only bounded known candidates; never invent IDs/coordinates/prices/hours/route times or bypass deterministic feasibility/confirmed apply. Preserve required selections and inputs on failure. No live charged call without approved credentials, quotas and cost controls.
- UX: extend Atlas progressively through basics/discovery/generate-edit; advanced controls remain optional, keyboard/mobile/reduced-motion and uncertainty are explicit. Local/cloud durability, editor and sharing still require P05/P06 tasks and their gates. Decorative3D is not added to planning.

## Alternatives and trade-offs

Rebuild the application, replace the planner with AI, auto-merge ambiguous places, replace legacy categories, fetch arbitrary Maps URLs or implement across unapproved gates: rejected. Adding every requested provider/map/storage library now is also rejected. Reuse existing code and platform APIs first; any added dependency still needs justification, security/license/bundle review and the applicable architecture approval. The staged order delays integration until its evidence and contracts can be reviewed.
