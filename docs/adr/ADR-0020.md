# ADR-0020 — RLS-preserving transactional trip mutations

Status ACCEPTED implementation detail under continued full implementation request,2026-10-22. Depends on P02-01 DONE. Does not change deployment/provider/gate policy.

Create canonical Master private tables and a SQL transactional repository before opening any owner endpoint. Tracker P02-02 and Master Phase02/P02-03 overlap on repositories. SQL transactions/constraints and safe initial RLS belong to P02-02; browser anonymous session, verified JWT owner adapter/API and live local-auth integration belong to P02-03. P02-04 closes complete security/replay coverage. Candidate/apply repository behavior is P04 and must not be faked by a P02 stub.

Direct authenticated table mutations would let callers bypass expected_version/idempotency. A postgres-owned SECURITY DEFINER mutation would bypass RLS. Instead use a dedicated NOLOGIN, NOSUPERUSER, NOBYPASSRLS, NOINHERIT writer role with only required table permissions. Narrow SECURITY DEFINER RPCs owned by this role have empty search_path and infer owner from auth.uid; policies still enforce owner identity. Authenticated gets owner SELECT and explicit RPC EXECUTE, never direct private writes. The role cannot create schema objects; default PUBLIC execution is revoked. Public share access is a separate later least-privilege resolver, never these owner functions.

Mutation commands validate expected_version and lock the owner-visible trip, return generic not-found for foreign IDs before disclosing version, and replace selected stops atomically. Idempotency keys are UUIDs, stored privately per owner with request SHA256 and minimal response; a retry returns its original result while a changed request with the same key conflicts. No raw private body or share token is logged. No Google-derived restricted coordinates/content are accepted as editorial data; catalog reference fields resolve from independently sourced published catalog, manual locations stay user-entered.

Keep source destination separation with composite foreign keys. Preserve retained scheduled metadata for existing IDs; reject dates/order/duration that invalidate locks unless an explicit owner edit confirms it. Future generation and apply must always preserve locks. Save must not silently remove planned or unscheduled stops that are still selected. A separate generate candidate can never mutate stored schedule.

Additional columns capture only Master/domain necessities (coordinate provenance, transport/hours metadata, versioned request results). No permanent Google route matrix caching, public edit token or recoverable-anonymous-ownership promise. Use current Supabase auth schema/roles in actual tests; fixtures are synthetic, not a replacement for verified-session integration in P02-03.

Alternatives rejected: unconstrained authenticated writes, bypass-RLS service-role mutation, in-memory persistence presented as cloud, or implementing apply-plan prematurely. Rollback task-only schema/tooling before release, later use reviewed forward migrations. Updated tests: writer-role properties, no direct write/anon grants, ownerA/B/null/forged identity, idempotent retry/mismatch, stale version, atomic rollback, city bounds and lock retention. Existing catalog42 tests and baseline checks remain mandatory.

Actual local pgTAP reached the first owner mutation and failed because postgres cannot delegate managed auth-schema USAGE (a direct GRANT emits a warning and does not grant access). ACL inspection and a minimal experiment reproduced this. Follow the official [Supabase custom-role Auth guidance](https://supabase.com/kb/troubleshooting/permission-errors-when-granting-custom-roles-access-to-the-auth-schema): a postgres-owned SECURITY DEFINER helper in non-exposed trip_private returns only auth.uid(), takes no inputs and reads no table. Grant helper execution only to authenticated/writer; keep writer without auth-schema access or inherited roles. All trip mutations still run as NOBYPASSRLS writer. Remove the ineffective GRANT rather than suppressing the warning. Preserve all68 assertions and add2 checks for this narrower boundary; rerun from reset, not from manually modified state.

Roundtrip inspection found that schedule sort_index cannot preserve the separate TripDraft.stops array order for unscheduled selections. A new assertion first failed on the absent selection_index column; strengthen the save fixture by reversing selection order relative to UUID ordering. Add selection_index0..29 with deferred unique(trip_id,selection_index), populated by JSON ordinality and read by future adapters. Scheduled ordering remains independent. This preserves user selection order across save/reload, including unscheduled entries. No assertions removed; private suite now71 cases, total113 with catalog.
